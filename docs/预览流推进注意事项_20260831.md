# 预览流推进注意事项

> 日期：2026-08-31，最终更新：2026-09-01
> 目的：记录手机 APP 预览流从问题分析、方案选择到最终落地的完整过程。

## 一、先回答核心问题

### 1. 现在要做预览流，是否还得先在本地手动切页面？

结论：**不应该把“本地手动切页面”当成前提条件。APP 侧做预览流时，UI 页面可以不变，重点是功能层 init/deinit 要成对。**

原因不是“页面完全无关”，而是当前实现里：

- 真正影响预览流的是**工作模式是否进入 `WORK_MODE_MOVIE`**，不是 LVGL 页面名字本身。
- 但当前热点页面 `page_sysmenu_hotspot.c` 在退出时会调用 `hotspot_exit_page()`，而这个函数会先关闭热点，再 `JL25_Stop()`。
- 也就是说，如果你为了手动切到本地视频页而退出热点页，往往会把 AP 和协议服务一起停掉，手机侧连接链路也就没了。

因此，**预览流要做成“APP 侧命令驱动模式切换 + 起流”**，而不是依赖人工先切到本地视频页面。  
UI 页面保持当前页即可，真正要管的是对应功能资源的开启和释放，不是 LVGL 页面跳转。

## 二、当前本地代码现状

### 1. 热点与协议服务生命周期

热点页中：

- 开热点：`WIFI_AP_Start()` 成功后调用 `JL25_Start()`
- 关热点：先 `JL25_Stop()`，再 `WIFI_AP_Stop()`
- 退出热点页：若热点开启，会先关热点

这意味着：

- 现阶段 AP/JL25 服务是**绑在热点页面生命周期上**的
- 一旦退出热点页，本地手动切别的页面并不能保持手机连接

### 2. 预览流依赖哪个工作模式

从 `moviemode.c` 看，`WORK_MODE_MOVIE` 打开时会初始化：

- `MEDIA_VideoInit()`
- `MEDIA_VencInit()`
- `MEDIA_AiInit()`
- `MEDIA_AencInit()`
- `MEDIA_StartAudioInTask()`
- `MEDIA_RecordSerInit()`
- `MEDIA_RtspSerInit()`

这说明手机预览流要复用现有媒体链路，**录像模式是最稳的起点**。

相反，`WORK_MODE_BOOT` 只是启动 UI，很多媒体链路并没有准备好。  
`bootmode.c` 里 `MODEMNG_BootFirstModeMsgProc()` 也只处理少量 `SETTING` 类消息，不处理 `START_REC`、`START_PIV`、`RTSP_INIT` 这类预览相关消息。

### 3. 旧实现对 APP 的处理方式

旧 `netctrl` 里已经体现了这条思路：

- `APP_GetDeviceAttr()` 会先检查当前是否在 `WORK_MODE_MOVIE`
- 如果不在，会先发 `EVENT_MODEMNG_MODESWITCH -> WORK_MODE_MOVIE`
- 等待切换成功后，再继续 APP 连接流程

旧 XML 协议里：

- `cmd=2015` 会触发 `EVENT_MODEMNG_RTSP_INIT / DEINIT`
- `cmd=2019` 返回 RTSP 地址
- RTSP 默认流名是 `APP_RTSP_NAME = "cvi_cam_phone_app"`

所以旧方案并不是“APP 连上就天然能看预览”，而是：

1. 先切到录像模式
2. 再起 RTSP
3. 再把地址告诉 APP

## 三、当前 JL25 / 兼容层里的缺口

> 本节及第四至第八节保留实现前的分析记录；最终实现结果以第九节和第十节为准。

### 1. `GetPreviewFrame` 还没实现

当前 `jl25_setup.c` 中：

- `/Setup?GetPreviewFrame` 直接返回 `404`

这代表 JL25 文档里的预览帧接口目前还是空的。

### 2. `mjpglive` / 8221 还没实现

当前仓库说明里已经明确：

- MJPG 预览流（8221）未实现
- `/mjpglive` 未接路由

因此如果要严格按 JL25 的 MJPG 方式做，当前是**从 0 到 1 补一条新流链路**。

### 3. 当前 APP 兼容层只“报地址”，没有真正起流

`jl25_app.c` 里：

- `/app/getmediainfo` 返回 `rtsp://<ip>/` 和端口 `6035`

但这里只是把地址告诉 APP，并没有：

- 保证当前已切到 `WORK_MODE_MOVIE`
- 调用 `EVENT_MODEMNG_RTSP_INIT`
- 管理 RTSP 起停状态

所以当前代码属于“**有地址描述，没有完整起流动作**”。

### 4. `jl25_setmode.c` 现在切的不是工作模式，只是菜单参数

当前：

- `/SetMode?PhotoCapture`
- `/SetMode?VideoCapture`

只是发送：

- `EVENT_MODEMNG_SETTING`
- `PARAM_MENU_RECORD_MODE = 0 / 1`

这不等于真正执行：

- `EVENT_MODEMNG_MODESWITCH -> WORK_MODE_PHOTO / WORK_MODE_MOVIE`

所以从预览流角度看，当前 `SetMode` 还不够。

### 5. 旧 CGI 兼容层对预览请求仍是“假成功”

当前 `jl25_legacy.c` 中，像这些旧 APP 请求：

- `action=set&property=Live&value=Enter`
- `action=set&property=StreamStatus&value=ON`
- `action=get&property=Camera.Preview.MJPEG.status.*`
- `action=get&property=Camera.Preview.RTSP.av`

多数只是返回成功或静态值，没有真正驱动 RTSP/MJPEG 状态机。

这也是为什么 APP 已经能连、能进相册，但预览流还不能直接工作。

## 四、要特别注意的设计点

### 1. 先确定第一阶段到底做哪种预览

建议把目标分成两种：

- 方案 A：**先复用现有 RTSP 6035**
- 方案 B：再补 JL25 文档里的 **MJPG 8221**

从当前代码基础看，**优先做 RTSP 6035 更现实**，因为本地已经有：

- `MEDIA_RtspSerInit()`
- `MEDIA_APP_RTSP_Init()`
- `MEDIA_APP_RTSP_DeInit()`
- `EVENT_MODEMNG_RTSP_INIT / DEINIT`

而 MJPG 8221 目前没有现成路由和发流实现。

### 2. 不要把“切本地页面”当成正式方案

测试时你可能会想：

- 本地先手动进视频页
- 再让手机连上看流

但这在当前实现里并不稳，因为：

- 热点页退出会关 AP
- APP 连接链路会断

所以正式方案应当是：

- AP 打开后保持服务在线
- APP 请求到来时，代码自动切 `WORK_MODE_MOVIE`
- 切换成功后起 RTSP

### 3. 模式切换必须做“等待成功”

旧 `netctrl` 已经做过这个动作：

- 发 `EVENT_MODEMNG_MODESWITCH`
- 轮询等待 `MODEMNG_GetCurWorkMode() == WORK_MODE_MOVIE`
- 超时失败则直接返回错误

这一步不能省。  
如果只发消息不等待，后续 RTSP init 很容易打在错误状态上。

### 4. 预览起流最好只在 `WORK_MODE_MOVIE` 执行

推荐约束：

- APP 预览入口统一先校验当前模式
- 不在 `WORK_MODE_MOVIE` 就先切
- 切换失败则不要伪造成功

否则容易出现：

- HTTP 返回看似成功
- APP 继续连 RTSP
- 实际没有任何视频数据

### 5. 需要明确“起流”与“报地址”的顺序

建议顺序：

1. 切模式到 `WORK_MODE_MOVIE`
2. 调 `EVENT_MODEMNG_RTSP_INIT`
3. 确认 RTSP 服务可用
4. 再返回媒体地址 / 允许 APP 拉流

不要先返回地址再慢慢起流，否则 APP 可能先发起拉流而失败。

### 6. 需要决定谁负责停流

至少要覆盖这些场景：

- APP 主动退出预览
- APP 断连
- 热点关闭
- 模式切到 `WORK_MODE_BOOT` / `WORK_MODE_PLAYBACK`

否则很容易留下：

- RTSP 服务还在跑
- 音视频回调没释放
- 再次进入预览时状态脏掉

### 7. 参考本地页面的退出收口原则

虽然预览流方案里 UI 页面不需要跟着切，但本地页面代码已经说明了一个原则：**进入时初始化，退出时成对释放**。  
这里参考 `page_photo.c` 和 `page_vedio.c` 不是要照搬它们的页面对象释放，而是参考它们的**功能资源收口原则**。

参考点：

- `page_photo.c`
  - 进入拍照页时会先释放上一页资源
  - 退出/切模式时会删除 AI 弹窗、取景框、缩放条、定时器、回调、语音弹窗等
  - 会删除 `date_timer`、连续拍照定时器、AI 结果定时器
  - 会取消 AI 线程、按键回调、笑脸回调，并把 `current_page_handler` 置空
  - 会在切模式前先停掉不该继续存在的页面资源
- `page_vedio.c`
  - 退出录像页时会先停止录像
  - 如果正在录像，会先发 `EVENT_MODEMNG_STOP_REC`
  - 会恢复触摸事件和音频输出状态
  - 再删除定时器、特效、取景框、缩放条、缩放相关 handler
  - 最后再切工作模式或回主页

对预览流来说，应该照这个思路做功能层 deinit：

- 停流前先停 RTSP / MJPG
- 如果预览流自己创建了回调、定时器、线程，就要对应释放
- 如果预览流自己改了状态位、占用了 RTSP 资源，就要对应恢复
- 如果预览流自己挂了录像链路，就要先解除绑定或停录像
- APP 断连、热点关闭、模式切走时都要走同一套收口

### 8. 对 APP 预览流更有参考价值的不是“切页”，而是“收口清单”

如果后面用 APP 侧来驱动预览流，建议把退出路径统一成一张功能清单，而不是绑 UI：

- 停止 RTSP 或 MJPG 发送
- 停止相关编码/推流回调
- 停止预览相关定时器或后台线程
- 如果占用了录像状态，先停录像
- 恢复预览流自己改动过的状态位
- 释放预览流自己创建的上下文
- 最后再决定是否切工作模式

也就是说，**UI 可以一直停在当前页面，但功能层必须像 `page_photo.c` / `page_vedio.c` 一样，保证自己创建的资源在退出时被释放干净。**

## 五、建议的实现路径

### 第一阶段建议

先做“APP 能拉到 RTSP 预览流”，不先做 MJPG 8221。

推荐顺序：

1. 在 APP/旧 CGI 的预览入口处补真实的“切到 `WORK_MODE_MOVIE`”
2. 补 `RTSP_INIT` / `RTSP_DEINIT` 调用
3. 让 `/app/getmediainfo` 返回的地址和实际 RTSP 流名对应起来
4. 跑通手机 APP 预览

### 第二阶段再考虑

等 RTSP 预览稳定后，再看是否需要补：

- `/Setup?GetPreviewFrame`
- `/mjpglive`
- 8221 MJPG 流
- `JpgSyncErrorAck` 的真实联动

## 七、联调时建议加的日志

至少建议加这些日志：

- 收到 APP 预览入口请求时打印 `path/query`
- 打印当前 `MODEMNG_GetCurWorkMode()`
- 打印是否发起 `EVENT_MODEMNG_MODESWITCH`
- 打印等待模式切换是否成功、耗时多少
- 打印是否发起 `EVENT_MODEMNG_RTSP_INIT / DEINIT`
- 打印 RTSP 流名、端口、返回给 APP 的地址

这样出现“APP 页面一直转圈”时，能很快区分是：

- 没切模式
- 模式没切成功
- 起流没执行
- 地址返回了但流名不对
- RTSP 服务有了但没出帧

## 八、功能层 Checklist

下面这份 checklist 只针对 APP 预览流自己的功能层资源，不包含 UI 页面对象。

### 1. init checklist

- 收到 APP 预览入口请求
- 记录当前 `MODEMNG_GetCurWorkMode()`
- 如果当前不在 `WORK_MODE_MOVIE`，先发 `EVENT_MODEMNG_MODESWITCH`
- 等待切到 `WORK_MODE_MOVIE` 成功，失败直接返回错误
- 按需调用 `EVENT_MODEMNG_RTSP_INIT`
- 确认 RTSP 流名、端口、返回地址一致
- 如果预览流自己注册了回调、线程、状态位，记录“已创建/已启用”状态

### 2. deinit checklist

- 停止 RTSP 或 MJPG 发送
- 解除预览流自己注册的推流回调
- 停止预览流自己创建的线程或定时器
- 恢复预览流自己改动过的状态位
- 如果预览流附带占用了录像状态，先停录像或解除绑定
- 清理预览流上下文，避免重复进入时状态脏掉

### 3. 必须覆盖的退出路径

- APP 主动退出预览
- APP 断连
- 热点关闭
- 模式切到 `WORK_MODE_BOOT`
- 模式切到 `WORK_MODE_PLAYBACK`
- 起流失败后的异常回滚

### 4. 最容易遗漏的点

- 只返回 RTSP 地址，没有真正 `RTSP_INIT`
- 只发 `MODESWITCH`，没有等待切换完成
- 预览退出后 RTSP 还在跑
- 第二次进入预览时沿用上次脏状态
- APP 断连时没有走和正常退出同一套 deinit

## 九、当前落地结果

截至 2026-09-01，手机预览流已按 `dc309` 本地实现跑通：

- 预览入口不再依赖功能层全局 `EVENT_MODEMNG_RTSP_INIT`
- 预览流固定为 `rtsp://192.168.169.1:554/liveRTSP/av4`
- 由 `dc309` 协议层本地创建 RTSP server 并挂接子码流回调
- 旧版全局 `media/mode/config` 改动已回退，避免影响 `sophcam` 功能层

## 十一、最终结论

- 预览流需要使用 `WORK_MODE_MOVIE` 下已准备好的视频编码链路，但不依赖本地人工切换页面。
- APP 预览请求到来后，协议层自动切换到录像工作模式并启动本地 RTSP。
- 当前实际使用的地址是 `rtsp://192.168.169.1:554/liveRTSP/av4`。
- 全局 RTSP service 方案已回退，最终实现只保留在 `dc309` 协议目录中。

## 十二、与拍照录像联动后的状态

截至 2026-09-01，APP 侧已经完成以下操作：

- 开始录像：协议层切换到 `WORK_MODE_MOVIE`，发送 `EVENT_MODEMNG_START_REC`，并等待录像状态生效。
- 停止录像：发送 `EVENT_MODEMNG_STOP_REC`，并等待录像状态结束。
- 拍照：停止 RTSP，切换到 `WORK_MODE_PHOTO`，发送 `EVENT_MODEMNG_START_PIV`，等待照片文件生成后切回录像模式并恢复 RTSP。
- 从相册返回预览：本地 RTSP 能够重新建立，APP 可继续预览。
