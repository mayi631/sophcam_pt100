# dc309 协议接入 APP 说明

> 日期：2026-09-03
> 最后更新：2026-09-04
> 说明：本文档描述 `applications/dashcam/ui/aicamera/dc309/src/protocol` 下 JL25 协议模块的设计思路、已完成能力、各文件职责，以及关键实现落点。

## 一、设计思路

核心原则是把 APP 接入能力收敛到 `dc309` 自己的协议层，不依赖全局 `thttpd/netctrl`，也不把功能挂到 `sophcam` 的通用媒体层。

实现方式如下：

1. 热点页面只负责开关 AP 和启动/停止协议服务。
2. 协议层自己起 `HTTP:80` 和事件端口 `TCP:8222`。
3. APP 的预览、拍照、录像、相册、下载都由 `dc309` 协议层完成路由和状态控制。
4. 预览流使用 `dc309` 协议层本地 RTSP，固定地址为 `rtsp://192.168.169.1:554/liveRTSP/av4`。
5. 拍照、录像、预览状态切换都在协议层内部完成，不再要求用户先手动切页面。

## 三、总体结构

协议入口链路：

`热点页面 -> JL25_Start() -> HTTP:80 + TCP:8222 -> JL25_HandleRequest() -> 各命令模块`

预览链路：

`APP 请求预览 -> jl25_preview_start() -> 自动切到录像模式 -> jl25_preview_rtsp_start() -> 子码流回调推送`

拍照链路：

`APP 拍照 -> 停止预览 -> 切到照片模式 -> 触发拍照事件 -> 等待照片落盘 -> 切回录像模式 -> 恢复预览`

录像链路：

`APP 开始录像 -> 确保录像模式 -> 触发开始录像事件 -> 等待录像状态生效`

## 五、主要功能落点

### 1. 协议服务主入口

主要在 `jl25_http.c`。

它负责：

- 启动/停止服务
- 监听 HTTP:80
- 监听 TCP:8222
- 管理 APP 连接
- 广播事件

### 2. 命令分发

主要在 `jl25_cmd.c`。

它负责：

- 把 URL 路径分发到对应模块
- 处理 `/Pin` 最小兼容
- 保证未知路径返回 404

### 3. 预览

主要在 `jl25_preview.c` + `preview_rtsp/jl25_preview_rtsp.c`。

`jl25_preview.c` 负责模式切换和预览生命周期；`jl25_preview_rtsp.c` 负责真正的 RTSP server 和视频帧发送。

### 4. 拍照与录像

主要在 `jl25_setup.c`，同时 `jl25_app.c`、`jl25_legacy.c` 也会转调同一套函数。

对应函数：

- `jl25_capture_start_record()`
- `jl25_capture_stop_record()`
- `jl25_capture_take_photo()`

### 5. 相册与下载

主要在 `jl25_storage.c`，`jl25_app.c` 负责 APP JSON 兼容。

对应能力：

- 文件列表
- 分页
- 缩略图
- 断点下载
- 删除文件

### 6. 旧版 APP 兼容

主要在 `jl25_legacy.c` 和 `jl25_appsock.c`。

兼容内容包括：

- `/cgi-bin/hisnet/getwifi.cgi`
- `/cgi-bin/Config.cgi`
- `/cammenu.xml`
- `/app/*`
- 旧 APP 连接状态保持

### 7. 模式切换

主要在 `jl25_setmode.c`。

它负责把 APP 的模式请求收敛到 `WORK_MODE_E`，并确保录像、拍照、存储、设置等页面切换时，状态机能同步到位。

## 六、当前协议策略

### 1. 录像模式

录像模式只保留必要控制，不再向 APP 暴露多余的可调设置。

### 2. 拍照模式

拍照时不依赖 `CONFIG_ENABLE_SNAP`，而是走照片模式路径，拍完再恢复预览。

### 3. 系统设置

系统设置保留：

- 格式化 SD 卡
- 录像分辨率（`rec_resolution`）
- 拍照分辨率（`photo_resolution`）

分辨率候选列表直接来自参数层的 `VideoSize` / `PhotoSize` 菜单表，与本地
设置页（`page_vediomenu_res.c` / `page_photomenu_res.c`）完全一致。设置动作
走 `EVENT_MODEMNG_SETTING` 消息（`PARAM_MENU_VIDEO_SIZE` /
`PARAM_MENU_PHOTO_SIZE` + 菜单下标），切换前会停掉 RTSP 预览，切换后恢复。
分段时长、麦克风、曝光以及其他通用设置仍不向 APP 设置页面暴露；
对应设置请求返回不支持。恢复出厂不作为普通参数项，而是通过
`/app/reset` 执行参数恢复流程。时间同步接口仍保留，用于 APP 与设备校时，
不作为设置页面菜单项。

### 4. WiFi 名称/密码

热点名称和密码不作为设置项对 APP 暴露，也不允许修改。为支持 APP 主动连接，
`/app/getdeviceattr` 的 `info.ssid` 会返回当前 AP 热点名称，供 APP 与手机当前连接的
WiFi 名称比较；密码仍不返回。旧版 WIFI 查询接口返回
HTTP 404 + `{"Result":-404}`，让 APP 将旧版 WIFI 能力判定为不存在；
HTTP 总入口会对 WIFI 相关 query 脱敏后再写入日志。

`/app/setting?param=enter/exit` 只作为设置页导航动作，返回标准成功结果；
实际设置能力由 `/app/capability` 控制，当前返回 `format=1`，并显式返回
`wifi/ssid/password/wifireboot/support_change_wifi_name_pwd=0`，其中 `reset=1`
表示恢复出厂可用，APP 调用 `/app/reset` 后执行参数恢复。同时
`getproductinfo` 使用原 `netctrl` 的 `cardv/sophgo/sophgo/cv` 产品标识，避免
APP 选择包含 WiFi 的默认设置模板。这样可避免
APP 因收到 `unsupported` 而回退到内置 WIFI 名称/密码菜单。

协议服务启动时会输出 `settings_policy=sd-format-only ... wifi_probe=http-404/absent product_template=legacy-cardv policy_version=5`；
关键 APP/旧 CGI 设置接口会输出实际 `http_status`、响应长度和非敏感响应内容。
如果日志仍出现 `response=200` 或 `HTTP 200`，应先确认设备是否替换了重新编译后的
`sophcam`；WIFI 相关响应内容统一显示为 `body=[redacted]`。

### 5. 热点状态与 APP 连接提示

- 普通 WiFi 参数中的 `WifiParam.Enable` 表示 STA/普通 WiFi 开关状态，不表示相机 AP 热点是否开启，不能直接用于热点页面的 `hs_switch`。
- 热点页面的开关、状态圆点和状态文字以 `JL25_IsRunning()` 为准；只有 AP 热点对应的 JL25 协议服务运行时才显示热点开启。设备开机时普通 WiFi 为开启状态，不应导致热点状态显示为开启。
- `getdeviceattr.ssid` 从 `PARAM_GetWifiParam()` 的 AP 配置 `WifiCfg.unCfg.stApCfg.stCfg.szWiFiSSID` 读取，APP 可用该值与手机当前连接的 WiFi 名称进行比较并主动连接。
- APP 成功建立 TCP `6035` 长连接，且设备成功创建客户端处理线程后，`jl25_appsock.c` 调用连接回调；热点页面使用 `str_language_connection_successful` 和 `top_notice_show_for()` 显示“连接成功”。
- 连接提示通过 `lv_async_call()` 投递到 LVGL 线程，协议线程不直接操作 LVGL 控件。

### 6. APP 恢复出厂设置

APP 调用 `/app/reset` 后，协议层执行 `jl25_factory_reset()`，不再发送
`UICOMM_SendSyncMsg(EVENT_MODEMNG_SETTING, PARAM_MENU_DEFAULT)`，避免进入底层
媒体销毁/重建流程。

恢复流程如下：

1. 通过 `PARAM_GetMediaComm()` 保存当前 `FocusPos` 和 `FocusPosLock`。
2. 通过 `PARAM_LoadFromDefBin()` 加载默认参数。
3. 使用堆内存保存 `PARAM_CFG_S`，避免约 300 KB 参数结构占用 HTTP 线程栈。
4. 恢复焦距标定值后调用 `PARAM_SetParam()` 和 `PARAM_SaveParam()`。
5. 释放堆内存并返回结果，不删除参数文件、不主动重启设备。

接口返回：

| 接口 | 成功 | 失败 |
|---|---|---|
| `/app/reset` | `{"result":0,"info":"set success."}` | `{"result":-1,"info":"set fail."}` |
| `/Setup?Reset` | `{"Result":0}` | `{"Result":-1}` |
| `Config.cgi` 的 `FactoryReset` | `0\nOK\n` | `-1` |

该功能不属于普通参数菜单项，但 `/app/capability` 必须返回 `reset=1`。
协议层只负责恢复参数和持久化，`moviemode.c`、`param.c` 等底层文件不需要修改。

## 九、整体审查结论

当前实现已经把 APP 接入链路收敛到 `dc309/src/protocol`，主链路清晰，旧兼容链路也保留了。

结论如下：

- 预览、拍照、录像、相册、下载都已经有明确落点，不再依赖全局功能层改动。
- `jl25_setup.c`、`jl25_preview.c`、`jl25_storage.c`、`jl25_setmode.c` 是当前最关键的业务文件。
- WiFi 名称/密码、分段时长、麦克风、曝光等按当前策略隐藏，不向 APP 暴露。
- 恢复出厂通过 `/app/reset` 正式执行，成功返回 `{"result":0,"info":"set success."}`，
  失败返回 `{"result":-1,"info":"set fail."}`，执行后不主动重启设备。
- `/app/getdeviceattr` 返回 AP 热点 SSID；普通 WiFi 的 STA 开关状态与热点 AP 状态分离。
- TCP `6035` 长连接建立成功后，设备 UI 显示“连接成功”提示。
- 录像分辨率 / 拍照分辨率由 `jl25_app.c` 的 `getparamitems`、`getparamvalue`、
  `setparamvalue` 三个接口承载，候选与当前值取自参数层菜单表，能力开关在
  `/app/capability` 中声明（`rec_resolution=1`、`photo_resolution=1`）。
- 目前文档描述与代码结构一致，适合作为交接说明。
- 分辨率设置接口修改未执行编译验证，需重新编译部署后观察板端日志。

## 十、本轮补充：APP 连接主动扫描与缩略图完整性

### 1. APP 连接后主动扫描

手机连接相机热点并打开 APP 后，APP 会建立 `TCP:6035` 长连接。
`jl25_appsock.c` 在长连接 accept 成功后调用
`jl25_storage_request_scan()`，由 `jl25_storage_guard.c` 创建后台扫描线程。

为兼容量产机的 APP 自动建链流程，协议层同时由 `jl25_discovery.c` 发送
UDP `49142` 状态通知。热点启动后先向 `192.168.169.255` 广播
`CAM_NUM_CHANGE` 和 `SD_STATUS`，收到 APP 的 HTTP 请求后再向其对端 IP
单播同样的消息。该通知用于触发 APP 建立或恢复 `TCP:6035`，与后续的
SD 卡文件扫描不是同一个机制。

扫描线程会先等待 FILEMNG 的初始扫描完成，再执行：

```text
FILEMNG_SCAN_COMPLETED
    -> FILEMNG_SetStorageStatus(NOT_AVAILABLE)
    -> 等待 FILEMNG worker 释放旧 DTCF 索引
    -> FILEMNG_SetStorageStatus(AVAILABLE)
    -> DTCF_Scan()
    -> FILEMNG_SCAN_COMPLETED
```

扫描过程中相册/下载请求会返回 `storage busy`，避免在 DTCF 销毁或重建期间访问无效句柄。
如果检测到无卡、挂载异常或录像已经开始，扫描会跳过或中止，并确保不会把文件管理状态长期留在
`NOT_AVAILABLE`。

部署后可在 `syslog/messages` 中看到：

```text
jl25 appsock client connected ...
jl25: APP connected, active file scan start
jl25: APP active file scan completed
```

### 2. 能力位

`/app/capability` 按新版协议返回能力字符串
`00000000300000100`。其中紧急相册使用 bit index 14（从 0 开始计数，
对应字符串第 15 个字符），值为 `1` 表示不支持；文件加锁能力保持关闭，
加锁文件仍允许删除。

### 3. APP 相册缩略图顶部正常、下部黑屏

该现象通常是 APP 收到的 JPEG 响应被截断，或者设备返回了生成未完成的 `.thumb` 文件。
旧实现存在固定 `512 KB` 读取限制，高分辨率照片在超过该长度后会被截断；同时仅判断缩略图文件
存在，无法识别半截 JPEG。

当前 `jl25_storage.c` 已调整为：

- 缩略图优先读取 `/mnt/sd/.thumb/PHOTO_SMALL` 或 `/mnt/sd/.thumb/MOVIE_SMALL`；
- 校验 JPEG 起始标记 `FF D8` 和结束标记 `FF D9`；
- 发现损坏或半截缩略图时删除并按需重新提取 APP0 缩略图；
- 缩略图发送按真实文件长度分块发送，不再受 `512 KB` 限制；
- 照片缩略图提取失败时，完整发送原始 JPEG 作为兼容回退；
- 视频不会再把完整 `.mov` 文件错误标记为 `image/jpeg` 返回。

相关日志：

```text
jl25 app getthumbnail fid=[...]
jl25: getthumb generated thumbnail, fid=[...]
jl25: getthumb fallback original, fid=[...]
```

### 1. `/app/getmediainfo`（协议 6.1.3）

当前响应在 `info` 中包含：

```json
{

  "info": {
    "rtsp": "rtsp://192.168.169.1:554/liveRTSP/av4",
    "transport": "udp",
    "port": 6035,
    "page": 1,
    "rectime": 1
  }
}
```

`rectime:1` 表示设备支持通过 `/app/getrecduration` 查询录像时长。缺少该字段时，部分 APP 不会轮询时长接口。

### 2. `/app/getsdinfo`（协议 6.1.4）

响应格式为 `{"result":0,"info":{"status":N,...}}`。状态码统一由
`jl25_storage_get_app_status()` 映射，当前映射如下：

| `status` | 含义 | 设备状态 |
|---:|---|---|
| 0 | 正常 | `CARD_STATE_AVAILABLE` / `CARD_STATE_FORMATED` |
| 1 | 未格式化或不可用 | `CARD_STATE_UNAVAILABLE` |
| 2 | 未插入 | `CARD_STATE_REMOVE` |
| 3 | 卡损坏 | `CARD_STATE_ERROR` |
| 4 | 卡已满 | `CARD_STATE_FULL_SPACE` |
| 10 | 写保护 | `CARD_STATE_READ_ONLY` |
| 11 | 卡速过慢 | `CARD_STATE_SLOW` |
| 12 | 文件系统/挂载异常 | `CARD_STATE_FSERROR` / `CARD_STATE_MOUNT_FAILED` |
| 13 | 正在格式化 | 协议层格式化任务进行中 |
| 99 | 检测中或未知 | `CARD_STATE_CHECKING` 及未覆盖状态 |

正常状态下额外返回 `free`、`total`，单位为 MiB；异常状态只返回 `status`。事件推送仍按 JL25 事件号发送：插卡 `Event:12`、拔卡 `Event:13`、错误 `Event:10`、卡满 `Event:11`、写保护 `Event:16`。

### 3. `/app/getrecduration`（协议 6.1.8）

响应格式为：

```json
{"result":0,"info":{"duration":56}}
```

`duration` 单位为秒，表示当前录像文件时长。协议层实现说明：

- 录像成功进入 `MEDIA_MOVIE_STATE_REC` 或 `MEDIA_MOVIE_STATE_LAPSE_REC` 后记录 `CLOCK_MONOTONIC` 起点；停止录像后清零。
- APP 第一次轮询晚于录像启动时，会在查询接口中延迟初始化计时起点。
- 计时使用单调时钟，不受系统校时影响，按整数秒返回。
- 读取 `PARAM_MEDIA_COMM_S.Record.ChnAttrs[0].SplitTime`；循环录像切换文件后按该毫秒值取模，因此返回当前分段文件时长，而不是整个录像会话累计时长。
- 非录像状态固定返回 `duration:0`。

相关实现位置：`jl25_app.c:449`（查询接口）、`jl25_app.c:537`（计时状态）、`jl25_setup.c:201/219`（录像开始/停止钩子）。

### 4. 联调检查

```bash
curl -s http://192.168.169.1/app/getmediainfo
curl -s http://192.168.169.1/app/getsdinfo
curl -s http://192.168.169.1/app/getrecduration
curl -s 'http://192.168.169.1/app/setparamvalue?param=rec&value=1'
sleep 3
curl -s http://192.168.169.1/app/getrecduration
curl -s 'http://192.168.169.1/app/setparamvalue?param=rec&value=0'
```

预期录像过程中 `duration` 随轮询增长，停止后恢复为 0；`syslog/messages` 可通过 `jl25` 前缀确认开始/停止录像和 SD 状态变化。

## 十二、远程录像生命周期、音频时间轴与 APP 断开保护

### 1. 远程录像入口统一

`/app/setparamvalue?param=rec&value=1|0`、`/app/startrecord`、`/app/stoprecord`、
旧版 `Config.cgi` 的 `recordon`/`recordoff`，以及 `/Setup?Shutter=1|0` 最终都收敛到
`jl25_setup.c` 的 `jl25_capture_start_record()` / `jl25_capture_stop_record()`。录像状态、
实际时长、录像前清理和 APP 断开清理都只能在该公共入口维护，不能分散到各 HTTP/CGI handler。

### 2. 录像前重建 recorder（不停止 JL25 RTSP）

连续 APP 录像曾出现以下日志：

```text
RECORDER_SendFrame: pts[...] earlier than start(...)
muxer_write_audio_packet: audio dts 2368 <= last 130256, adjust to 130257
```

含义是新文件仍消费到上一录像会话残留的帧，muxer 保留旧 audio DTS 并把后续每一个
音频包压成 `last + 1`。MOV 音轨时间轴被压缩后，APP 回放会跳秒、设备本地播放会无声。

当前在 `jl25_capture_start_record()` 发送 `EVENT_MODEMNG_START_REC` 前执行：

```c
MEDIA_RecordSerDeInit();
MEDIA_RecordSerInit();
```

它仅重建 record service、recorder/muxer、音频回调和录像缓存；不调用
`jl25_preview_stop()`、`MEDIA_RtspSerDeInit()`，也不切换工作模式。APP 预览服务和网络
连接保持，允许初始化期间出现短暂画面抖动。开始/停止由 `s_jl25_capture_mutex` 串行化。
任何重建失败都必须使本次开始录像返回失败，不能继续发送开始录像事件。

### 3. APP 断开自动停止远程录像

旧逻辑中，TCP:6035 客户端断开只减少客户端计数；`JL25_Stop()`（关闭热点路径）只停止
HTTP/TCP/UDP 协议服务。两处均不停止录像，导致：

```text
APP 开始远程录像 -> APP 断开或设备关闭热点 -> 相机仍继续写卡录像
```

当前实现：

1. `jl25_capture_start_record()` 成功后设置 `s_jl25_remote_recording=1`；本地 UI 开始的
   录像不设置此标记。
2. `jl25_appsock.c` 的 TCP:6035 客户端断开并递减计数后触发 APP 断开回调。
3. 没有其他 TCP:6035 APP 客户端、且当前标记为远程录像时，回调调用
   `jl25_capture_stop_record()`。
4. `JL25_Stop()` 也调用 `jl25_capture_protocol_stopping()`，覆盖设备退出热点页面/关闭 AP。
5. 停止前原子清除远程录像标记，多个客户端同时断开时最多下发一次停止录像事件。

涉及文件：

| 文件 | 责任 |
|---|---|
| `jl25_setup.c` | 远程录像标记、断开及协议停止时的条件性停止、录像互斥。 |
| `jl25_appsock.c` | TCP:6035 断开回调。 |
| `jl25_http.c` | 注册回调，协议停止时清理远程录像。 |
| `jl25_protocol.h` / `jl25_internal.h` | 回调及内部清理接口声明。 |

边界要求：APP 显式停止时清除标记；多个 APP 客户端时仅最后一个断开才停；本地 UI 录像不因
APP 断开而停止；远程录像若已被其他系统事件停止，断开清理安全返回。

### 4. 本轮验收

1. 连续两次 APP 录像各 7～10 秒，两个文件均有声音，日志不应出现
   `audio dts <= last ... adjust`。
2. APP 录像时关闭 APP 或手机 WiFi，应看到：

   ```text
   jl25 APP disconnected, stop remote recording
   EVENT_MODEMNG_STOP_REC
   ```

3. APP 录像时退出热点页/关闭热点，应看到：

   ```text
   jl25 protocol stopping, stop remote recording
   EVENT_MODEMNG_STOP_REC
   ```

4. 设备本地启动录像后关闭热点或让 APP 断开，录像不应被停止。
